# Key decisions

All decisions below are **locked** by the project brief unless marked *Proposed*. Locked decisions change only with explicit approval. Section references point to [architecture.md](architecture.md).

| # | Decision area | Options considered | Recommendation | Rationale |
|---|---|---|---|---|
| 1 | Environment groups | (a) one cluster per environment; (b) one cluster for all non-prod; (c) Dev/Stage, UAT, Prod groups | **(c)** Dev/Stage share a group; UAT and Prod separate (§4) | Dev and stage share exposure, certificates and channel, so separate clusters add cost and an ArgoCD instance for little gain. UAT needs external exposure and its own upgrade stage. Prod needs STABLE plus DR. |
| 2 | Project model | (a) project per customer; (b) project per customer per env; (c) fixed shared projects by function and env side | **(c)** ~12 fixed projects; dedicated project only for `isolation: dedicated` (§2) | Per-customer projects mean 800+ projects, with quota, IAM and billing sprawl, and they grow with customers. Fixed projects keep IAM, VPC-SC and Shared VPC simple. Most quotas are per project per region, so regions add headroom. |
| 3 | Placement and sizing | (a) sizing tiers (S/M/L); (b) manual cluster choice; (c) region-only input + automatic placement into cells | **(c)** (§3) | Users, data volume and SLA are unknown at onboarding, so tiers would be guesses. A Git-only placement job is deterministic, testable offline and needs no human choice. |
| 4 | Database tenancy | (a) instance per customer; (b) shared database with `tenant_id`; (c) schema per customer; (d) **database per customer per env, schema per product** | **(d)** on pooled instances (§8) | Hard boundary via `CONNECT`, native per-database export/import for seed down, restore, move and offboarding. Products stay separable inside one customer. Far cheaper than (a). (b) relies on application correctness. |
| 5 | Data sharing between a customer's environments | (a) live cross-env connections; (b) custom ETL/sync; (c) **three one-way audited flows** (shared reference, promote up, seed down) | **(c)** (§9) | No live coupling or credential crossing between envs; GCP-native operations only; sanitization and verification are mandatory before anything leaves prod. |
| 6 | Cloud SQL encryption keys | (a) instance per customer for a per-customer CMEK; (b) platform key per pooled instance + app-level envelope encryption with the customer key; (c) no CMEK | **(b)** (§10) | CMEK applies per instance, not per database. Envelope encryption of sensitive columns keeps crypto-shredding per customer. Customers who need an instance key take `isolation: dedicated`. |
| 7 | ArgoCD topology | (a) one global instance; (b) instance per cluster; (c) **one per environment group** (3) | **(c)** (§14) | Non-prod tooling can never touch prod. 3 instances are manageable by 5 engineers. Split by region later if needed. |
| 8 | Kubernetes objects: tenant chart vs Terraform | (a) Terraform `kubernetes`/`helm` providers; (b) **tenant Helm chart via ArgoCD** | **(b)** (§14) | Terraform stays on Google APIs (no cluster credentials in TF, no provider-ordering problems). ArgoCD self-heals drift and applies the same GitOps path as workloads. |
| 9 | DR model | (a) backup/restore only; (b) **warm standby with a dedicated DR cluster**; (c) active-active | **(b)** default, `dr: hot-standby` opt-in (§12) | Meets RTO ~30 min / RPO ~5 min at about 2× the fixed DB footprint. Active-active would need multi-writer data, which Cloud SQL doesn't offer. A dedicated DR cluster avoids doubling load on a peer cell. |
| 10 | DR granularity | (a) per customer; (b) **per cell** | **(b)** | Cloud SQL fails over per instance. One instance per prod cell makes the failover unit exact and testable. |
| 11 | API authentication | (a) Apigee / API gateway; (b) **JWT at Istio (GKE) and a shared library (Cloud Run, MIG)**, Cloud Armor at the edge | **(b)** (§11) | No gateway cost or extra hop. Apigee can be inserted between the LB and the backends later without changes to them. |
| 12 | Runner pools | (a) GitHub-hosted runners; (b) **self-hosted, separate non-prod and prod pools inside the VPC-SC perimeters** | **(b)** (§15) | Perimeters block hosted runners. Separate pools keep non-prod identities out of prod. Ephemeral, WIF-authenticated, no keys. |
| 13 | Image path to prod | (a) prod builds; (b) shared registry; (c) **build once in non-prod, promote by digest with a prod attestation** | **(c)** (§15) | One artifact, same bits in every env. The only cross-perimeter access is the prod promoter reading non-prod. No key crosses a perimeter. |
| 14 | Version divergence | (a) customer forks/branches; (b) **one codebase, pinned immutable versions per customer per env, config → flags → extension points → variant image** | **(b)** (§7) | Keeps one code line. The support window (N-2) bounds the matrix. Variant images are opt-in and built from overlays, never forks. |
| 15 | Cloud Run and MIG tenant isolation | (a) project per customer; (b) **service/MIG per customer per product per env, env GSA identity, invoker IAM, per-tenant network tag firewall** | **(b)** (§11) | Keeps the fixed project count. The data boundary is still per customer, since the identity can only reach its own containers. The weaker network boundary is covered by default-deny tags and the isolation tests. |
| 16 | Persistent storage | (a) stateful by default; (b) **stateless by default; GKE PVC by catalog exception; no Filestore** | **(b)** (§8) | Data that may be shared or recovered lives in Cloud SQL/GCS/BigQuery. PVCs hold only rebuildable data, so they never enter data flows. |
| 17 | Data services catalog | (a) any GCP service on request; (b) **Cloud SQL PostgreSQL, GCS, BigQuery, Pub/Sub only** | **(b)** (§8) | Every service needs isolation, DR, sanitization and offboarding design. A small catalog keeps those guarantees. Additions are a catalog change. |
| 18 | Labels and cost | (a) per-customer cost allocation engine; (b) **mandatory identification labels, platform-level cost only** | **(b)** (§16) | Customers are billed by subscription. Labels serve operations, audit and offboarding. |
| 19 | Terraform orchestration | (a) Terragrunt; (b) **plain directories per layer/state, generated from templates, composition module holds logic** | **(b)** (§17) | Fewer tools for 5 engineers. Changed-path detection and generated directories cover what Terragrunt would. |
| 20 | Terraform scope | (a) Terraform manages DB grants via a Postgres provider; (b) **Terraform uses Google APIs only; the bootstrap job applies grants and schemas** | **(b)** (§8) | No DB network access or passwords in Terraform. The bootstrap login is an IAM user with `cloudsqlsuperuser` assigned via the Admin API (verification V10). |
| 21 | Region quotas for Cloud Run *(added by verification)* | (a) ignore until hit; (b) **track `quotas.cloudRunServices` in inventory, enforce in placement, trigger project if the increase is refused** | **(b)** | 1,000 services per project per region is reachable at ~250 customers in one region ([V3](gcp-verification.md#v3-cloud-run-services-per-region-per-project)). |
| 22 | ArgoCD cluster endpoint *(changed with approval, 2026-11-23)* | (a) private IP endpoint + global access + authorized networks; (b) **DNS-based control-plane endpoint, IP endpoints disabled, access by IAM** | **(b)** | Google's current recommendation. Access is governed by IAM (`container.clusters.connect`), not IP allowlists. It works from any region through Private Google Access and is covered by VPC-SC. L2 no longer maintains authorized networks ([V7](gcp-verification.md#v7-argocd-access-to-private-clusters)). |
| 23 | Cluster subnets *(added in Phase 2)* | (a) one GKE subnet per region with secondary ranges per cluster; (b) **one node subnet per cluster** | **(b)** | A subnet has at most 30 secondary ranges, so (a) caps a region at 15 clusters. (b) gives each cell its own `/24` node subnet with its own pod and service ranges (architecture §3). |
| 24 | Per-customer shared states *(added in Phase 2)* | (a) only one state per customer per env; (b) **one state per env + `keys-nonprod`, `keys-prod` and `exchange` states per customer** | **(b)** | Key rings are per environment group (Dev/Stage serves two env states), and exchange resources serve all 4 envs while sitting in their own perimeter. They need an owner whose pipeline identity is in the right perimeter. |
| 25 | Prod and UAT edge failover *(added in Phase 2)* | (a) automatic LB failover to DR backends; (b) **DR backends attached with capacity 0; failover flips `drActive` for the cell in Git** | **(b)** | Until the cell's Cloud SQL DR replica is promoted, DR backends would serve against a read-only replica. Failover is per cell and run by the runbook (RTO ~30 min), so the LB switch is a reviewed Git change. |
